# entities/ — Living Snapshots

## What this workspace is for

Living state of every stakeholder — people (clients + family) and projects (business + offers). Source of truth for what's happening with each entity right now. Snapshots are updated live during sessions, not just at session close.

## Structure

```
entities/
├── people/
│   ├── [person-slug].md     — One file per person: clients, family members, key contacts
│   └── family.md            — Family unit snapshot
└── projects/
    ├── snapshot.md          — DoAnythingNow entity state
    ├── content-strategy.md  — Weekly posting schedule + platform map
    └── offers/              — One file per offer line (type: profile)
```

Each person and project is a flat file — no per-entity subfolders. When a relationship grows complex enough to need multiple files, promote to a subfolder.

## People ↔ Projects linking

Clients are under `entities/people/` and may be linked to active projects or offers. When a client engagement maps to a specific offer or project thread, note it in both files:

- In the person file: reference the offer/project under `current_focus` or `next_actions`
- In the project/offer file: reference the person under `Clients` or `Current Engagements`

This keeps the relationship bidirectional without duplicating state.

## Snapshot schema

All people and project snapshots use this frontmatter:

```yaml
---
entity: [Name]
type: snapshot
last_updated: YYYY-MM-DD
current_state: "[One paragraph]"
current_focus:
  - "Priority 1"
open_questions:
  - "What are we trying to figure out?"
tensions:
  - "Things pulling in different directions"
next_actions:
  - "Concrete next steps"
---
```

Offer files use `type: profile` and have a different schema — see `offers/_template.md`.

## Process

1. Read the specific snapshot before working with that entity — not the digest (too compressed for deep work)
2. Update frontmatter fields live when state shifts — don't batch for `/wrap`
3. Meetings live in `meetings/` and link back here via a `## Meetings` section
4. The digest (`_digest.md`) is a compressed read-only view — generated by `/wrap`, never edited directly

## Skills that apply here

| Skill | When |
|---|---|
| `/meeting` | After any client or external meeting — auto-extracts to this entity file |
| `/summary` | Updates entity file and DPL from a meeting; runs inside `/meeting` or standalone |
| `/client-vault` | When onboarding a new client — builds hub index + project files + one-pager |
| `/wrap` | Parallel-writes entity updates at session close |
